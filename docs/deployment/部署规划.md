## 1. 目标与前置

把 ListenWise 从本地开发部署成「公网可访问、能真实转写」的应用。

**前置条件**（满足后再启动部署）：
- 本地功能成熟：至少 P0 核心（上传转写 + 说话人分离 + 逐字稿查看/编辑/导出）跑通。
- 已完成「§5 最大风险」的验证——否则方案可能不成立。

## 2. 推荐架构

复用用户已有的免费栈（与知识工程项目同一套）：

| 层 | 选型 | 说明 |
|----|------|------|
| 前端 | **Vercel** | Next.js 原生支持，全球 CDN；知识工程前端在用【已验证先例】 |
| 后端 API | **Render**（Web Service, Python） | FastAPI；知识工程后端在用，`render.yaml` 模板现成【已验证先例】 |
| 转写任务 | **Render Background Worker**（Celery）或改 FastAPI BackgroundTasks | 见 §4.1【待决策】 |
| 数据库 | **Supabase PostgreSQL** | 知识工程在用【已验证先例】 |
| 缓存/队列 | **Upstash Redis** 或 Render Redis | Celery broker（若保留 Celery）【待验证】 |
| 文件存储 | **阿里云 OSS** 或 Supabase Storage | 见 §4.4【待决策】 |
| ASR/LLM | 阿里云百炼 Fun-ASR / qwen（公网 API） | 见 §5 最大风险 |

```
用户浏览器
   │
   ├── 前端(Vercel, Next.js)
   │      └── /api → 后端(Render)
   │
后端(Render, FastAPI)
   ├── Postgres(Supabase)
   ├── Redis(Upstash)  ←→  Celery Worker(Render Background Worker)
   │                              └── 阿里云 Fun-ASR + OSS  ⚠️ 海外→国内
   └── 文件存储(OSS / Supabase Storage)
```

## 3. 可复用知识工程的先例

知识工程后端架构与 ListenWise 几乎一致（FastAPI + SQLAlchemy 2.0 async + asyncpg + Alembic + pydantic-settings），其部署经验可直接借鉴：

- `knowledge-engineering/backend/render.yaml`：runtime python / `buildCommand: pip install -r requirements.txt` / `healthCheckPath: /docs` / autoDeploy。
- 生产架构：前端 Vercel + 后端 Render + 数据库 Supabase（知识工程 CLAUDE.md「🚀 部署」节）。
- 参考文档：知识工程的 `ONLINE_DEPLOYMENT.md`、`QUICK_DEPLOY.md`、`ROLLBACK_GUIDE.md`。

**ListenWise 要补的差异**：Celery worker、Redis、文件持久化、以及最关键的——ASR 是国内阿里云 API（知识工程用海外 LLM，不存在跨境访问问题）。

## 4. 关键挑战与应对

### 4.1 Celery worker（转写常驻进程）【待决策】

ListenWise 转写靠 Celery worker 异步执行。Render 免费 Web Service 会休眠且不含常驻 worker。两个方案：

| 方案 | 做法 | 取舍 |
|------|------|------|
| **A. 保留 Celery** | Render 加一个 Background Worker 服务（约 $7/月）+ Redis broker | 架构不变，可靠；有月费 |
| **B. 去 Celery，改 BackgroundTasks** | 转写改用 FastAPI `BackgroundTasks` 在 Web 进程内异步跑，去掉 Celery + Redis | 省钱省组件；但长转写期间 Web 实例不能休眠，且单实例并发有限。MVP 单用户低频可接受 |

> 建议：MVP 先走 **B**（最省，匹配单用户低频）；用量上来再切 A。需要把 `tasks/transcribe.py` 的 Celery 任务抽成可被两种方式调用的函数。

### 4.2 Redis【待验证】

仅方案 A 需要。用 Upstash（免费 10000 命令/天）或 Render Redis。方案 B 不需要。

### 4.3 数据库迁移到 Supabase

- Supabase 建项目 → 拿连接串（注意 Supabase 用 `postgresql://`，asyncpg 用 `postgresql+asyncpg://`）。
- `DATABASE_URL` 指向 Supabase；`alembic upgrade head` 跑迁移（含 enum、ModelProviderConfig 表）。
- 注意 Supabase 连接池（pgbouncer）与 asyncpg 的兼容：用 Session Pooler 端口或 direct connection。

### 4.4 文件持久化【待决策】

Render 文件系统临时（重启/部署即丢）。上传的音频在转写期间必须可访问。

- 现状：上传存本地 `uploads/`，转写时 `OssUtils.upload()` 再传到 DashScope OSS。
- 方案 B（同进程）：本地临时暂存 → 上传 DashScope OSS → 转写 → 删本地，够用（不依赖持久化）。
- 方案 A（worker 分离进程）：Web 与 Worker 不共享文件系统，需先把上传文件落到 **共享存储**（阿里云 OSS / Supabase Storage），Worker 从存储取。
- 长期：用户要回看/重转，原音频应持久化到 OSS（带过期清理策略）。

## 5. ⚠️ 最大风险：海外 Render 访问国内阿里云（必须先验证）

**这是决定方案成不成的关键，未验证前不要正式部署。**

- 知识工程用 OpenAI/Anthropic（海外），Render（海外）访问无障碍。
- **ListenWise 用阿里云百炼 Fun-ASR + DashScope OSS（均在国内）**。Render 实例在海外（US/Singapore），跨境访问阿里云：
  - OSS 上传音频（可能几十 MB）：跨境带宽慢 → 上传耗时长。
  - REST 提交 + 轮询：延迟高，可能超时。
  - 稳定性：跨境网络抖动、偶发失败。

**验证方案（部署前先做）**：
1. 在 Render 部署一个最小测试端点（或临时 Web Service），跑一次真实 Fun-ASR 转写（上传一个几 MB 音频），测量：OSS 上传耗时、转写总耗时、成功率（多跑几次）。
2. Render region 选 **Singapore**（离中国比 US 近），对比延迟。
3. 判定标准：若 1 小时音频端到端 < 5 分钟且稳定成功 → 方案成立；若频繁超时/失败 → 走备选。

**备选（若海外访问阿里云不可行）**：
- **换国内可部署点**：阿里云函数计算/ECS、腾讯云、Zeabur（有国内节点）等部署后端，贴近阿里云 API。前端仍可 Vercel。
- **换 ASR 为海外可达的服务**：因 D1「按能力维度可配置 Provider」，可换成有海外节点的 ASR（如 Qwen3-ASR 国际站、或其他海外 ASR）。但要重新验证中文效果。
- 注：这一步可能推翻「全 Vercel+Render」的设想，所以**必须前置验证**。

## 6. 分阶段部署计划

| 阶段 | 动作 | 产出/验收 |
|------|------|-----------|
| **0 风险验证** | 在 Render(Singapore) 跑通一次真实 Fun-ASR 转写，测延迟/成功率 | 决定方案成立 or 走备选（§5） |

## 7. 环境变量清单（Render 后端）

```
DATABASE_URL=postgresql+asyncpg://...supabase...
REDIS_URL=...                    # 方案 A 才需要
DASHSCOPE_API_KEY=sk-...         # 百炼 key（ASR + qwen 共用）
ASR_PROVIDER=fun_asr
LLM_API_KEY=sk-...               # 同 DASHSCOPE_API_KEY
APP_SECRET_KEY=<32位随机>          # Fernet 主密钥（生产必须设，加密 DB 中的 provider key）
OSS_ACCESS_KEY_ID / OSS_ACCESS_KEY_SECRET / OSS_BUCKET_NAME / OSS_ENDPOINT   # 若文件走自有 OSS
CORS_ORIGINS=https://<vercel前端域名>
```

> 注意：现 `main.py` 的 CORS `allow_origins` 硬编码 `http://localhost:3000`，部署前需改为读环境变量、加生产前端域名。

## 10. 专项待办（2026-06-03 记录，今天不开发）

用户提出、留待后续专门处理的两个问题。此处只做问题界定与子项清单，不展开实现方案。

### 10.1 音频与文本的存储体系

现状：音频存后端本地 `uploads/`（临时目录，部署即丢）；文本（逐字稿 segments、摘要 summary/outline/highlights/keywords）存 Postgres。

需要决策的子问题：

| 维度 | 待决问题 |
|------|---------|
| 音频存哪 | 对象存储选型（阿里云 OSS / Supabase Storage）；与 §4.4 部署期持久化合并考虑 |
| 音频留多久 | 转写完即删，还是保留供回看/重转？保留则需生命周期与过期清理策略、单用户配额 |
| 原音频下载 | 是否允许用户下载原始音频；涉及外链签名/鉴权 |
| 文本容量 | 长音频逐字稿可能很大，Postgres JSONB 是否够用，是否需要冷热分层/归档 |
| 文本检索 | 是否要全文检索（pg 全文索引 / 向量检索）；现列表搜索仅前端按标题过滤 |

→ 部署期临时文件问题见 [§4.4](#44-文件持久化待决策)；此处关注的是**产品侧数据生命周期**，比 §4.4 更宽。

### 10.2 公网发布的应用层准备

§5–§9 已覆盖基础设施（网络验证、部署架构、环境变量、成本）。但**应用层**仍是当前代码的盲区，公网开放前必须补：

| 类别 | 待办 | 现状风险 |
|------|------|---------|
| 鉴权 | 接入真实登录/账号体系 | 现 `user_id=1` 全程硬编码，无登录 |
| 多租户隔离 | 所有查询按当前用户过滤 | 现记录列表/详情全局共享，任何人可见全部数据 |
| 密钥安全 | 生产必设 `APP_SECRET_KEY`（Fernet 主密钥），加密 DB 中 provider key | 无主密钥时降级为明文存储 |
| 上传防护 | 文件大小/类型/时长校验、限流 | 上传校验尚未做（P0 模块4 待开发） |
| 成本护栏 | ASR/LLM 按量计费，公网需配额/防刷，避免被滥用刷量 | 无限流，开放即有刷量风险 |
| CORS | 收紧到生产前端域名 | 现 `main.py` 硬编码 `localhost:3000`（§7 已注明） |
| 合规 | 用户音频/文本隐私说明；若用国内域名或服务器涉及 ICP 备案 | 未评估 |

→ 这些属「从能用到能公开给别人用」的差距，建议在 §6 阶段 4（前端上线）之前作为独立批次处理。

## 附：与本地开发环境的差异

本地（已验证可跑）：postgresql@16 + redis(brew) + uvicorn + celery worker + DASHSCOPE key 直连阿里云（国内网络，快）。
云端最大变化：**网络位置**（海外 Render → 国内阿里云），这正是 §5 要验证的核心。
