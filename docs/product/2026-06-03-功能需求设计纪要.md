## 2. 模型 & Provider 配置体系（横切，三功能共用）

### 2.1 能力分层（对应 D1）

「模型设置」页 = 三块独立配置，各选一个 Provider：

| 能力 | 用途 | 配置项 |
|---|---|---|
| **ASR 转写** | 音频转文字（文件异步 / 实时流式） | Provider + API Key + Endpoint + 模型名 + 区域 |
| **翻译** | 实时/离线多语翻译（可开关） | 同上 |
| **LLM 总结** | 纪要、要点、章节、播客提炼 | 同上 |

- API Key 落库需加密存储。
- MVP 单用户/单租户，配置全局生效；多租户隔离放后续。

### 2.2 首发 Provider 选型【已确认：B 路线】

调研结论：阿里系有两条路线——
- **A. 通义听悟 API**：转写+摘要+导图一站式，但单价高（实时翻译 4 元/时），AI 输出格式受厂商约束。
- **B. 百炼裸 ASR + 自选 LLM**：Fun-ASR 文件转写支持 **公网音频 URL 输入 + 说话人分离 + 12h/2GB**，Paraformer ~0.288 元/时最便宜；总结用 qwen/DeepSeek 自研，格式自控。

**已确认走 B 路线**：性价比高、AI 输出可自研（契合首页"智能总结要点"的卡片式产物），且 Fun-ASR 的 URL 输入能力让播客功能"拿到音频地址直接转"链路最短。架构上因 D1 可配置，后续可切到 A 或其他厂商（火山/腾讯/讯飞）。

**为什么不选听悟 A（决策记录，2026-06-03 评估）**：A 的优势是开箱即用、AI 产物成熟、省自研调优；但被以下三条否决——

| 维度 | A 通义听悟 API | B 百炼 ASR + 自研 LLM |
|---|---|---|
| ASR 成本 | 0.6 元/时 | 0.288 元/时 |
| 产物可定制 | 弱（格式厂商定） | 强（schema 自主） |
| 与 D1「按能力维度配置」架构 | ✗ ASR+翻译+LLM 捆成黑盒，拆不开 | ✓ ASR/LLM 独立可配 |
| 三功能技术栈 | 播客单独整包，易分裂 | ASR/LLM 三处复用 |
| 厂商绑定 | 强 | 弱（LLM 可换 qwen/DeepSeek） |

核心：① 听悟整包与 D1 的"能力维度独立配置"架构冲突；② 我们已定的播客 schema（outline 带时间戳、highlights 逐字）+ 首页卡片式产物需要自研 LLM 才能精确产出；③ 成本与三功能技术栈统一。代价（自研总结需调优）已接受。

## 3. 数据模型影响（供后端参考）

- **Recording 新增 `source` 字段**：`upload | podcast | realtime`，区分三种来源（现有 `scene_type` 为 legacy，可逐步弃用）。
- **新增模型配置表**（如 `model_provider_config`）：`capability(asr|translate|llm) + provider + api_key(加密) + endpoint + model + region + enabled`。
- **播客来源补充字段**：`source_url`（原始链接）、`feed_title`/`episode_title`（可选）。
- **AI 产物存储**：摘要/章节/要点/QA 建议独立表或 Recording 的 JSONB 字段（沿用现有 Transcript JSONB 模式）。
- 实时转录的 partial/final 增量不直接落库，结束后合并为标准 Transcript（与文件转写同构）。

## 5. 三功能需求设计

### 5.1 P0 · 上传音视频转写

**场景**：网课、已有录音文件、会议录音转文字（最成熟，现有基础覆盖一半）。

**核心链路**：
```
上传(音/视频) → 后端抽音轨(ffmpeg) → 前置校验(格式/采样率) → 云 ASR 文件异步转写
→ 轮询结果 → 归一化 segments → 落库 → 查看(音字联动)/编辑/导出 →(可选)LLM 总结
```

**需求清单**：
- 【已确认 D6】格式与上限：音频 ≤500MB、视频 ≤6GB、时长 ≤6h；视频后端用 ffmpeg 抽音轨。
- 【已确认 D6】采样率前置校验：<16k 直接拒绝并提示，避免低质音频浪费转写费（上传环节 ffprobe）。
- 【建议待定】多文件上传队列 + 进度可视（听悟支持 50 并发），而非单文件阻塞。
- 【已确认隐含】说话人区分 + 时间戳（导出 SRT/VTT 依赖时间戳；分人依赖 Fun-ASR）。
- 【已确认 D7】LLM 总结 = 用户**手动触发**，按字数门槛（≥250 字）生成，不默认烧 token。
- 【开放】长音频失败重试 / 任务超时 / 重复回调处理策略。

### 5.2 P1 · 播客链接转写

**场景**：订阅/输入播客链接，自动转写 + 智能总结。本质 = 拿到音频 URL 后复用 P0 文件转写链路 + LLM 总结。

**核心链路**：
```
输入链接 → 解析出音频 URL → 后端取音频(或直传 URL 给 ASR) → 转写 → LLM 总结 → 落库
```

**输入形态（D2 已确认）**：

| 输入类型 | 可行性 | MVP |
|---|---|---|
| ① 直接音频文件 URL（.mp3/.m4a 直链） | ✅ 合规、Fun-ASR 直接吃 URL，链路最短 | ✅ 做 |
| ② 播客 RSS 链接 → 解析 enclosure 选单集 | ✅ 合规（开放协议），听悟/Podwise 都走这条 | ✅ 做 |
| ③ 播客平台单集网页链接（小宇宙/Apple 单集页） | ⚠️ 需爬页面解析音频地址，覆盖不稳 + 合规灰区 | ❌ 放后续 |
| ④ 视频平台直链（B站/YouTube/抖音） | ❌ 听悟明确回避（服务条款/版权红线） | ❌ 不做 |

> 调研印证：通义听悟、Podwise 都以 **播客 RSS** 为链接转写的一等公民，主动回避视频平台直链。ListenWise MVP 锁定「①直接音频 URL + ②RSS 单集解析」。

**播客总结输出 schema（⑤ 已定，Podwise + 通义听悟双参照）**

> 两个产品的播客 AI 产物高度重合（听悟：摘要/章节速览/思维导图/问答/关键词；Podwise：Summary/Outline/Mindmap/Highlights/Keywords），交叉验证了下面的 schema。**MVP 做 4 块，v2 做衍生视图**。

```jsonc
// —— MVP 必做 4 块 ——
{
  "summary": {                   // 1. 摘要(分层,不是一段话)
    "tldr": "string",            //    1-3 句全文概述
    "outline": [                 //    带时间戳分节大纲 = 两家口碑核心,最该做
      { "title": "string", "start_sec": "number", "points": ["string"] }
    ]
  },
  "transcript": [                // 2. 逐字稿(说话人+时间戳+音字联动,复用 P0)
    { "speaker": "string|null", "start_sec": "number", "end_sec": "number", "text": "string" }
  ],
  "highlights": [                // 3. 金句(AI 自动抽,逐字引用,附时间戳)
    { "quote": "string", "start_sec": "number", "speaker": "string|null" }
  ],
  "keywords": [                  // 4. 关键词(词条+轻量释义)
    { "term": "string", "explanation": "string" }
  ]
}
```
**产物触发策略（D8，用户定 2026-06-03）**：

| 产物 | 触发 | 说明 |
|---|---|---|
| transcript 逐字稿 | **自动** | 输入链接后核心产出 |
| summary（tldr + outline） | **自动** | 播客核心价值"以读代听"，优先产出 |
| highlights 金句 | **手动触发** | 用户点按生成 |
| keywords 关键词 | **手动触发** | 同上，可与金句一次 LLM 调用产出 |

> 与上传场景 D7 的差异：上传场景 LLM 总结整体手动触发；播客把 summary 当核心刚需自动产出，仅金句/关键词手动。

- **生成效率**：手动触发时 highlights + keywords 在**同一 LLM 调用里多任务产出**，省 token 省时延。
- **超长节目**：summary 走 map-reduce（分段总结再聚合），不一次性塞全文。
- **逐字约束**：highlights 必须从 transcript 原文取句 + 附 `start_sec`，禁改写（否则金句卡失真、无法跳转）。

**v2 衍生视图（不单独存 AI 产物）**：
- **Mindmap**：从 `summary.outline` 层级机械转换，前端 markmap 渲染。
- **Shownotes 聚合**：summary+outline+highlights+keywords 汇成可导出 Markdown 笔记（嘉宾/外链靠 LLM 推测，标「可编辑」）。
- **导出**：先 Markdown（覆盖 Obsidian/Logseq），再 Notion/Readwise。
- **明确不做**：独立 Clips 片段、AI 问答（对内容提问）、自定义术语表/热词 —— 均已砍。

**其余需求**：
- 【开放】版权边界：下载第三方播客音频转写，限个人学习用途的声明。
- 【开放】RSS 选集 UI：解析 feed 后列出剧集供选择的交互。

### 5.3 P2 · 实时转录

**场景**：会议/访谈现场，边说边出字。工程风险最高（全新 WebSocket 流式链路）。

**核心链路**：
```
浏览器采集 → 分片 → WebSocket → 云 ASR 流式(fun-asr-realtime) → partial/final 增量
→ 前端实时展示 →(可选)同步翻译/结束后总结 → 结束合并落库(同构 Transcript)
```

**需求清单**：
- 【建议待定】翻译做成**可选开关**，默认关（听悟实时翻译 4 元/时，是转写近 7 倍，需让用户感知高成本）。
- 【建议待定】总结：**结束后一次性生成**，非过程中滚动（成本/复杂度低）。
- 【建议待定】说话人区分：实时 diarization 不稳，默认近似标"发言人 1/2"，不强制。
- 【建议待定】字幕形态≥2 种：滚动逐字稿 / 当前句大字幕（会议记录 vs 演讲字幕两类用途）。
- 【开放】可靠性：断线重连、partial 回滚、录音中途崩溃恢复 —— 实时链路最大工程风险。
- 【开放】并发/声道模型：单路 mic vs 多路混音。

## 6. 暂不纳入（明确划界，避免 scope 蔓延）
