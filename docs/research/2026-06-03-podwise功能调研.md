# Podwise (podwise.ai) 调研报告 — 为 ListenWise 播客总结 schema 提供参考

> 调研日期 2026-06-03。信息来源以官方渠道(少数派作者复盘、即刻官方号、阮一峰 weekly 自荐、官方复盘长文)为主,辅以官网与第三方评测。具体 episode 页需登录,未直接抓取,产物形态依据官方文字描述+评测交叉验证,个别细节标注「未确认」。

## 一、整体定位与目标用户

- **定位**:面向播客**听众**的 AI 知识管理/学习工具(slogan「AI Copilot for Podcast Listeners」「Podcast knowledge at 10x speed」)。核心解决「播客信息密度低、时长动辄 2-5 小时、听完记不住、难检索」的痛点,把音频转成**可读、可搜、可沉淀**的结构化知识。
- **关键定位差异**:它不是给创作者做营销物料的工具(那是 Castmagic / Shownotes.ai 那一类),而是**给消费者做"听后即得知识卡"**。产品有意把播放器缩小、把文字内容最大化——「以读辅听」是其交互哲学。
- **目标用户**:重度播客听众、研究者、知识工作者,尤其是原本要在「转录工具 + ChatGPT + Notion」之间手工拼流程的人。
- **背景**:三人小团队(《硬地骇客》播客主理人)2023 年三个月做出,典型独立 AI 应用。
- 来源:[少数派官方复盘](https://sspai.com/post/83452)、[阮一峰 weekly 自荐](https://github.com/ruanyf/weekly/issues/3844)、[官方复盘长文](https://blog.zhexuan.org/archives/Podwise.html)

## 二、逐个拆解 7 类 AI 产物

> 重要校准:Podwise 官方文案里反复出现的核心产物是 **Summary / Outline / Mindmap / Transcript / Keywords / Highlights(金句)**。截图 tab 中的 **Clips** 和 **Shownotes** 在官方文字里描述较弱——下面按最可信的解读拆解,弱证据处标「未确认」。

### 1. Summary 摘要 —— 分层,非一段话
- **内容**:对全集核心观点的浓缩。
- **形态**:**分层结构**,不是单段话。拆成两个层级配合使用:
  - **全文总结**(段落式概述,几句话讲清这期讲了什么);
  - **Outline 大纲**(见下,带时间戳的逐节要点)。
- **生成方式**:先按章节(segment)分段总结,再聚合成全文总结(map-reduce 式)。
- **价值**:30 秒判断「这期值不值得听 / 听哪段」。

### 2. Outline 大纲(常与 Summary 同屏)—— 带时间戳的分节要点
- **内容**:把整集切成若干**主题章节**,每节一句话要点。官方称「3 分钟读完一集大纲」。
- **形态**:**列表 / 层级 outline,每节带时间戳**,点击可跳转到音频对应位置。这是 Podwise 最被称道的功能——「有了时间维度的大纲,能从 4-5 小时节目里精准挑感兴趣的段落针对性收听」。
- **结构**:`章节标题 + 起始时间戳 + 该节要点(1-N 条)`。这是 ListenWise 最该抄的一块。

### 3. Mindmap 思维导图 —— 层级树,可交互
- **内容**:把全集观点和**它们之间的关系**抽成脑图结构。
- **形态**:桌面端放射状思维导图;移动端改为**纵向树形**便于窄屏阅读(响应式适配)。
- **交互**:可视化展示、便于整理延伸;支持导出。
- **价值**:看结构、看话题间逻辑关系,而非线性读。

### 4. Transcript 逐字稿 —— 带说话人、时间戳、音字联动
- **内容**:全集精确转录文本,是其余所有产物的底座。
- **形态**:**三个关键特性都有**:说话人识别(向量化区分)、时间戳、音字联动(点任意文字跳到对应音频时刻)。
- **可搜索**:全文可搜,「在整个库里找任意一句话/话题/时刻」。
- **结构**:`[说话人][时间戳] 文本段` 的序列。

### 5. Keywords 关键词 —— 词条 + 解释(带百科性质)
- **内容**:从全集抽取的关键术语/概念。
- **形态**:**词条带解释**,不是裸标签。流程里有「解释关键词」独立步骤,对专有名词给简短释义(轻量百科)。
- **附加**:关键词与高亮可生成**精美图片卡片**,方便社交分享。

### 6. Highlights 高亮 / 金句 —— AI 自动提取(非用户标注)
- **内容**:AI 从全文挑出的「值得记住的话 / 金句 / 关键洞察」。
- **形态**:**AI 自动划重点**,在统一 prompt 框架里与「章节总结、关键词抽取」一道完成。
- **附加**:可一键生成**可分享的金句图卡**。
- **结构**:`金句原文 +(可选)时间戳/说话人 + 配图卡`。用户侧也可在 transcript 手动选段保存,但主力是 AI 自动。

### 7. Clips 片段 与 Shownotes 节目笔记 —— 弱证据,需产品内确认
- **Clips**:官方未明确定义为独立切片功能。最可信解读:(a)可引用/可分享片段(与 Highlights 重叠);(b)用户在 transcript 手动框选。**是否 AI 自动切独立 clip、是否生成音/视频短片未确认**。Podwise 整体偏「读」,做短视频概率低。建议 ListenWise 把 Clips 理解为「Highlights 的可分享片段视图」,而非新增一类产物。
- **Shownotes**:在听众侧最可能是**结构化整集笔记的聚合视图**(summary + outline + keywords + highlights + 嘉宾/链接 汇成一篇可发布/收藏的笔记)。**具体字段未确认**。

## 三、输入方式

- **添加方式**(官方明确):订阅/关注、**RSS**、搜索、直接链接、**小宇宙**、**Apple Podcasts**。
- **中文播客支持**:明确支持中英文及中英混合;**集成小宇宙**。
- 还可**上传本地音频文件**。
- **复用机制**:头部节目「一次转录、多用户复用」,默认预处理 Top 100,降低边际成本。ListenWise 若平台化应考虑「同一 episode 只算一次」。

## 四、AI 处理流程(双流水线)

**流水线 A(转录)**:下载音频 → 语言探测 → 预采样 → Whisper 转录 → 分段 → 优化 → 入库
**流水线 B(理解)**:加载转录 → 分段 → LLM 多任务(章节总结 + 抽 highlights + 抽关键词)→ 生成全文总结 + 关键词释义 + 思维导图 → 入库

- **模型**(2023-24 时点,当前未确认):GPT-3.5/4 与 Gemini Pro 混用(Gemini 当时免费降本);转录用 Whisper(含本地部署降本);说话人识别用向量化。
- 「Whisper 转录 + LLM map-reduce 总结 + 多任务单 prompt」架构对 ListenWise 完全可复用。

## 五、导出 / 同步

- 可把 summary、highlights、mindmap、笔记导出/推送到:**Notion、Readwise(Reader)、Obsidian、Logseq、纯 Markdown**。
- 知识管理定位的关键闭环——「产结构化知识 → 推进用户第二大脑」。

## 六、价格模式(freemium + 订阅 + 买断)

- Free:每月 4 集 AI 增强额度。Standard ~$5.90/月。Pro ~$11.90/月。**一次性买断**占总支付约 30%。

## 七、对 ListenWise 播客总结输出 schema 的建议

### MVP 先做这 4 块(投入产出比最高,互相依赖最少)

```jsonc
{
  "episode": {
    "id": "string", "title": "string", "podcast_name": "string",
    "source_url": "string", "duration_sec": "number", "language": "string"
  },
  // —— MVP 必做 ——
  "summary": {                   // 1. 摘要(分层,不要一段话)
    "tldr": "string",            // 1-3 句全文概述
    "outline": [                 // 带时间戳分节大纲 = Podwise 最强项
      { "title": "string", "start_sec": "number", "points": ["string"] }
    ]
  },
  "transcript": [                // 2. 逐字稿(说话人+时间戳+音字联动)
    { "speaker": "string|null", "start_sec": "number", "end_sec": "number", "text": "string" }
  ],
  "highlights": [                // 3. 金句(AI 自动抽,逐字)
    { "quote": "string", "start_sec": "number", "speaker": "string|null" }
  ],
  "keywords": [                  // 4. 关键词(词条+释义)
    { "term": "string", "explanation": "string" }
  ]
}
```

**为什么是这 4 块**:`summary.outline`(带时间戳分节大纲)是 Podwise 口碑核心、感知最强;`transcript` 是底座、ListenWise 已有能力近零增量;`highlights` 与 `keywords` 可在生成 outline 的**同一 LLM 调用里多任务产出**(省 token、省时延)。

### v2 再做
- **Mindmap**:从 `summary.outline` 层级机械转换(章节→一级,要点→子节点),前端 markmap 渲染。**只是 outline 的衍生视图,不单独存 schema**。
- **Shownotes 聚合视图**:summary + outline + highlights + keywords + 嘉宾/外链 汇成可导出 Markdown 笔记。前端聚合 + 导出模板,非新 AI 产物。
- **导出集成**:先 Markdown(覆盖 Obsidian/Logseq),再 Notion/Readwise API。
- **Q&A(对话整集)**:基于 transcript 做 RAG,独立功能,非 schema 一部分。

### 明确不做
- **独立 Clips 切片**:Podwise 自己都没做强。用 `highlights[].start_sec` + transcript 区间即可覆盖「可分享片段」。
- **金句/关键词图卡**:纯前端渲染,不进 schema。

### 边界情况(主动提示)
1. 说话人识别在双人以上/串台/背景音乐场景准确率骤降——`speaker` 必须允许 `null`,前端优雅降级「说话人未知」。
2. outline 时间戳依赖转录时间对齐——生成 outline 时应让 LLM **引用 transcript 段的 `start_sec`**,而非自己编时间。
3. 中文播客嘉宾/外链口播少有结构化信息,`shownotes` 的 guests/links 靠 LLM 推测易错,标「AI 推测,可编辑」。
4. 超长节目(4-5h)token 超限——summary 必须 map-reduce(分段总结再聚合)。
5. highlights 必须**逐字引用**(从 transcript 原文取句、附 start_sec,禁改写),否则金句卡失真且无法跳转。
