# PodNote 竞品调研（2026-06-11）

> 与 ListenWise **撞型最严重的直接竞品**：同样中文播客、同样阿里云系基建、同样「转写 + AI 分析」，且已上线 App Store、有订阅收入。
> 本文技术架构部分来自用户**亲手扒接口**（podnote.com/reader 的网络请求），产品面来自联网补全。

## 三、技术架构（用户实测扒接口）⭐ 本文最有价值部分

### 3.1 三个接口分工清晰（关键架构思想）

| 接口 | 返回 | 职责 |
|---|---|---|
| `GET .../pod_note/meta/{id}` | 标题、节目名、shownotes、intro、状态 | **元信息** |
| `GET .../pod_note/content/{id}` | QA、keyTakeaways、notableQuotes、viewpoints | **AI 解读** |
| `GET .../pod_note/audio/{id}` | `data.ASR.asrResult` 逐句文字稿 + 音频状态 | **文字稿 + 音频** |

> **文字稿单独从 audio/ASR 数据源取，不和 shownotes、AI 内容混在一起。** 这正是你之前在 ListenWise 踩的坑（抓公众号时文字稿 / shownotes / 精编混淆）的正解。

### 3.2 文字稿数据模型

```ts
type AsrSegment = {
  id: number
  speaker: string      // ⚠️ 实测值是"十分吸引"（节目名），不是 A/B/C → 见下方分析
  startTime: number    // 毫秒
  endTime: number      // 毫秒
  content: string
  blockId: number      // 段落分组键
}
```

`audio` 接口示例：
```json
{
  "audioStatus": "READY",
  "audioSource": "oss",
  "duration": 6843000,
  "ASR": { "asrResult": [ { "id":0, "speaker":"十分吸引", "startTime":2110, "endTime":7430, "content":"嗨，大家好...", "blockId":0 } ] }
}
```

**前端加工**：按 `startTime` 排序 → 按 `blockId` 分组 → 同 blockId 的句子合并成**段落** → 每段保留 `contentList` 用于「点击跳转 / 按时间高亮 / AI 引用定位」。

### 3.3 转写流程（异步任务编排）

```
已转写 → 直接 GET audio/{id} 拿 asrResult（这集返回 1497 条）

未转写 → 点 Transcribe
  → POST /pod_note/process { pod_note_id }
  → 拿 task_id，轮询 GET /pod_note/process/status?task_id=xxx
  → 完成后 GET /pod_note/audio/{id} 取结果

后台：获取播客音频 → 提取音频信息 → ASR 转写 → AI 分析 → 保存结果
```

### 3.4 基础设施

- **音频存储**：阿里云 OSS 香港 `podnoteaudio.oss-cn-hongkong.aliyuncs.com`
- **大小限制**：file too large / limit **200MB**
- **ASR provider**：**未公开**。前端只调 PodNote 自家后端；错误提示有 "ASR provider timed out" / "Audio source is temporarily unreachable by ASR provider"。
  - 推测：阿里云 OSS（香港）+ 中文播客 + 200MB 限制 → 很可能是**阿里云/百炼/DashScope** 系，但**无实锤**（前端没暴露 DashScope/Whisper/AssemblyAI 等供应商名）。

## 四、对 ListenWise 的三个直接启示 ⭐

### 启示 1：数据模型「三分」—— meta / content / audio 各自独立
ListenWise 现在把 segments / summary / outline / highlights / keywords **全塞在一个 `Transcript` 表**。PodNote 拆成三个独立数据源：元信息、AI 解读、文字稿互不污染。
→ **这就是你反复强调的「文字稿不要和 shownotes / AI 内容混」的工程化答案。** ListenWise 可参考此拆分，至少在 API 层把「文字稿」「AI 产物」「元信息」分清。

### 启示 2：`blockId` 分段合并 —— 逐句存、按段显
PodNote 底层存逐句（带时间戳），但用 `blockId` 把碎句合并成可读段落，同时保留句级 `contentList` 支撑「点击跳转 / 高亮跟随 / AI 引用定位」。
→ ListenWise 的 segments 目前是逐句平铺，可借鉴 blockId 分段，让文字稿更像「段落」而非「字幕条」。

### 启示 3：AI 解读结构更丰富
PodNote 的 `content` = **QA + keyTakeaways + notableQuotes + viewpoints**；ListenWise 现在是 summary + outline + highlights + keywords。
→ 可借鉴的两块：**QA（自动问答对）** 和 **viewpoints（观点提炼）**，比单纯 tldr+大纲更适合「快速消化一期播客」。

## 五、与 ListenWise 对标

### PodNote 有而 ListenWise 没有
| 能力 | 借鉴价值 |
|---|---|
| 思维导图（Mind Map）可视化 | ⭐⭐ 结构化消化 |
| 自动 QA 问答对 + 观点提炼 viewpoints | ⭐⭐⭐ 比纯摘要更好用 |
| 单集翻译 | ⭐ 跨语言场景 |
| iOS 原生 App + 已商业化订阅 | 产品成熟度领先 |

### ListenWise 有而 PodNote 没有（差异化护城河）
| 能力 | 说明 |
|---|---|
| **真说话人分离 A/B/C** | PodNote 的 `speaker` 字段实测是**节目名**（"十分吸引"），**不是真正的多人分离** —— 这是 ListenWise 用 Fun-ASR 单声道 diarization 的**实打实差异化** |
| **会议录音场景**（专注记笔记） | PodNote 纯听众侧，无会议 |
| **SRT / VTT 字幕导出** | PodNote 只到 Markdown / 纯文本 |
| **AI 摘要结合用户手记笔记** | PodNote 摘要是全自动，不吃用户笔记 |
| **音字联动内嵌播放器**（V4 底部条） | PodNote Web 也有跳转，但 App 端是外跳播放器 App |

### 一个共同的市场真空
**「一键转某播客的全部历史单集」PodNote 也没有**（它是单集级 process）。你做免费抓十分吸引时踩的痛点，PodNote / SpotScribe / Podwise 全都没覆盖 —— **RSS 订阅追踪 + 批量历史补录，仍是显性差异化机会。**

## 七、技术栈反推：用了哪家 ASR 和 LLM ⭐（三路 workflow 侦查）

> 后端是黑盒（前端没暴露供应商），以下是从 **asrResult 字段特征 + 阿里云基建信号 + 公司背景** 三路反推。硬信号与推测分开标注。

### 7.1 一句话结论

> **阿里云百炼录音文件识别（Fun-ASR / Paraformer-v2，开了说话人分离）+ 通义千问 Qwen（做 QA/观点/翻译 + 自动给说话人起名）+ 自家后端轮询编排** —— 跟 ListenWise 几乎同栈。
>
> 🔄 **2026-06-11 据用户实测页面截图修正**：原反推「未开 diarization / speaker=节目名兜底」被推翻 —— 实际开了分离且做了自动命名，详见 7.3。

| 层 | 判断 | 置信度 |
|---|---|---|
| ASR 在**阿里云生态** | 高 | ~70% |
| 具体是 Fun-ASR / Paraformer-v2 | 中 | ~50-55% |
| LLM 是 **Qwen** | 中（纯生态推断，零直接证据） | ~50-55% |

### 7.2 硬信号（已实查 / 已扒到）

- 音频存**阿里云 OSS 香港** + DNS=阿里云万网（hichina）+ 服务器 IP=**AS45102 Alibaba(HK)** → 全栈阿里云基本实锤。
- DashScope 录音识别返回 `begin_time/end_time` 是**毫秒整数**，与 PodNote 的 `startTime/endTime` 单位一致。
- 公司双实体：**Genvox Inc.**（网页版权）/ **WhalesGrowth Inc.**（iOS app 版权，沪 ICP 备 2022012462）→ 上海背景小团队。
- 错误文案「ASR provider timed out」「Audio source temporarily unreachable by ASR provider」= **托管 ASR 主动拉取音频 URL** 的工作模式。

### 7.3 关键修正：实际开了说话人分离 + LLM 自动命名（据用户实测截图）

> 用户实测页面截图推翻了原反推。Transcript 的 speaker 不是单一节目名，而是**多个说话人交替**：
> - 「**石磊** 00:07 我是石磊。」
> - 「**十分吸引** 00:08 我是明姐。」
> - 「**石磊** 00:09 我们希望做到系统化洞察…」
>
> 且 Quote（金句）区按说话人正确标注（石磊 / 胡克勤）。

修正后的判断：
1. **PodNote 开了说话人分离**（分出 2-3 个说话人），原「没开 diarization」结论作废。
2. **做了自动说话人命名**：把 ASR 的 `speaker_id`（0/1）映射成**真实姓名**（石磊、胡克勤）—— 比 A/B/C 更进一步。
3. **映射有瑕疵**：把「明姐 / 敏姐（刘敏）」错标成节目名「十分吸引」。所以 `speaker=节目名` 只发生在**识别失败的说话人**上，是兜底，不是全部。

**怎么做到的（推测）**：Intro 有主播名单（"创始人胡克勤、基金合伙人石磊及嘉宾刘敏"）→ ASR diarization 分出说话人段 → 用 **LLM** 根据「我是石磊」这类自我介绍 + 主播名单，把 `speaker_id` 对应到姓名。映射对了石磊 / 胡克勤，但"明姐"昵称没匹配上名单里的"刘敏"，兜底成节目名。

**这个修正反而强化「用了 LLM(Qwen)」的判断** —— 自动说话人命名需要 LLM 推理，ASR 单独做不到。

### 7.4 字段映射层

PodNote 把 ASR 原生 `text/begin_time`（snake_case）统一映射成 `content/startTime`（camelCase）+ 自建 `blockId` 段落分组 → 所以**靠字段名认不出供应商**，只能靠基建 + 时间单位 + 中文 + speaker 异常综合推断。

### 7.5 被排除的供应商

- **OpenAI Whisper**：`start/end` 是秒（浮点）、无 speaker，结构完全不符。
- **AssemblyAI / Deepgram**：美国服务访问香港 OSS 延迟高、中文精度弱、`speaker=A/B` 而非节目名。
- **讯飞**：字段 `bg/ed/onebest/speaker`(数字)，海外接入差。
- **Azure / Google**：时间格式/合规/可访问性都不符。
- **LLM 侧排除**：Claude（大陆 IP 限制）、Gemini、Azure OpenAI。

### 7.6 对 ListenWise 的 4 个参考

1. **印证选型没走偏**：PodNote（若同栈）和 ListenWise 都押阿里云百炼中文 ASR → 「中文播客 = 阿里云 ASR」是行业默认最优解。**PodNote 技术上没有秘密武器，差异化在产品层**。
2. **反超点 = 自动说话人命名**（据截图修正）：原以为说话人分离是 ListenWise 护城河，但截图证明 PodNote 不仅分了说话人，还**自动映射成真实姓名**（石磊 / 胡克勤），比 ListenWise 的「A/B/C + 手动改名」更自动。**这是 ListenWise 该借鉴的点**：用 Intro/Shownotes 的主播名单 + LLM，自动给 speaker 起名，省去手动改名。（PodNote 的映射偶有瑕疵 —— 明姐→节目名，说明不简单，但方向值得做。）
3. **借鉴「先文稿后解读」渐进返回**：PodNote 把 `audio`（文字稿，先返回）和 `content`（AI 解读，异步出）拆成**两个独立接口**，降低首屏等待感。ListenWise 现在是一锅出。
4. **后端归一化 ASR 输出**：PodNote 的字段映射层（snake→camel + blockId）让将来换 ASR 供应商不动前端，是值得采用的解耦实践。

### 7.7 把推测变实锤（用户可亲手扒，按优先级）

1. **抓服务端→ASR 的出站包**（Charles/mitmproxy 看后端是否直连 `dashscope.aliyuncs.com`）—— 唯一能实锤 ASR 的方法。
2. **上传单人 vs 多人播客对比 `speaker` 值** —— 都返回节目名=没开 diarization；出现 0/1=开了，推断要修。
3. **传纯英文播客看质量** —— 英文明显差=阿里云中文特化坐实；接近=可能 Whisper，推翻结论。
4. **解包 `PodNote.ipa`** 搜 binary 有没有 `dashscope-sdk / aliyun / nls` 残留。
